## 一、项目背景与目标

汇报里把 KV cache 分组思想归纳为三个轴：

- **Token block**（按固定位置分组）
- **Window block**（按时间窗口分组）
- **Semantic block**（按语义结构分组）

老师反馈的需求是：

> 用最简单的框架实现一个 **token block / window block + TurboQuant** 的 KV cache 量化方法。不要 vLLM 等复杂框架，可用 transformers 实现；分组涉及 PagedAttention 思想可借鉴但不强求。目标是不复杂但可扩展的代码。

本子模块就是这个需求的落地，**不动**已有 `turboquant/` 任何文件，新增一个 `block_cache/` 子包，约 800 行 Python。

## 二、TurboQuant 原语（理解前提）

TurboQuant 已存在于 `turboquant/compressors_v3.py` 中的 `MSECompressor` 类。它的算法是**两步走**：

```
输入向量 v ∈ ℝᴰ
     │
     ① 归一化     v̂ = v / ‖v‖              ← 单位球面，存 ‖v‖
     │
     ② 随机旋转   r = Π v̂                    ← Π 是固定的随机正交矩阵
     │            （旋转后每个坐标 ≈ N(0, 1/D) 高斯）
     │
     ③ 逐坐标量化  iⱼ = argmin |rⱼ − cₖ|     ← Lloyd-Max 码本
     │
     输出: indices (D 个 uint, 位宽=bits) + ‖v‖ (fp16)
```

**为什么要旋转？** Lloyd-Max 码本是按**单位方差高斯**校准的最优量化器。原始 K/V 向量分布很乱，但归一化 + 随机旋转后每个坐标都近似独立同分布的高斯——一个码本就能覆盖所有坐标，且接近信息论最优。

**TurboQuant 的接口很窄**：
- `compress(v) → {indices, norm}`
- `decompress({indices, norm}) → v_hat`

整个 block_cache 框架就是绕着这个接口造的。

## 四、各层代码详解

### Layer 1a — 块容器（`blocks.py`）

#### `KVBlock`：固定容量 KV 槽位 + 状态机

```
FILLING  ──── append 满 ────►  SEALED  ──── policy 决定 ────►  COMPRESSED
(fp16)                          (fp16)                           (TurboQuant)
```

```python
@dataclass
class KVBlock:
    block_size: int          # 默认 16
    state: BlockState        # FILLING / SEALED / COMPRESSED
    current_len: int
    fp16_k, fp16_v           # (B, H, ≤block_size, D) — 状态 != COMPRESSED 时
    compressed_k, compressed_v  # dict — 状态 = COMPRESSED 时
    importance: float        # 预留给"块级驱逐"扩展
```

#### `BlockTable`：单层有序块列表

`append(k, v)` 自动切片、跨块路由、报告"哪些块满了"：

```python
def append(self, k, v):
    sealed = []
    while 还有 token 没放完:
        if 当前块满了 or 没有当前块:
            new_block()
        overflow = 当前块.append_fp16(k, v)
        if 当前块.state == SEALED:
            sealed.append(它)
    return sealed   # ← 给 policy 看的"新封口的块"
```

### Layer 1b — 量化包装（`quantizer.py`）

`BlockMSECompressor` 是连接框架和 TurboQuant 的桥梁：

```python
class BlockMSECompressor:
    def __init__(self, head_dim, bits, seed, granularity, device):
        self._inner = MSECompressor(head_dim, bits, seed, device)  # ← TurboQuant 原语
        self.granularity = granularity   # 'per-vector' | 'per-block'

    def compress(self, states):  # states: (B, H, S, D)
        if granularity == 'per-vector':
            return self._inner.compress(states)   # 直接走 TurboQuant
        else:
            # SKVQ 风格 group-level：用块均值作为单一 scale
            block_norm = mean L2 norm 跨 S 维
            scaled = states / block_norm           # 不再每 token 一个 norm
            rotated = scaled @ self._inner.Pi.T   # ← 共用 TurboQuant 的 Π
            indices = argmin |rotated - centroids| # ← 共用 TurboQuant 的码本
            return {idx_bytes, block_norm, ...}
```

**这里就是"我的代码"和"TurboQuant"的接缝**：
- per-vector 模式 = 100% 委托给 `MSECompressor.compress()`，行为不变
- per-block 模式 = 自己重写归一化步骤，但**复用 TurboQuant 的旋转矩阵 Π 和 Lloyd-Max 码本**

算法上的完整性不打破，只是把"每 token 存一个 norm"改成"每块存一个 norm"，对应 SKVQ 论文里的 group-level 量化思想。

### Layer 2 — 分组策略（`policies.py`）

策略只回答一个问题：**新 SEALED 的块要不要立刻量化？哪些老 SEALED 的块也该量化了？**

```python
class GroupingPolicy(ABC):
    @abstractmethod
    def on_seal(self, sealed: list[KVBlock], table: BlockTable) -> list[KVBlock]:
        """返回应该被立刻压缩的块的子集"""
```

三种实现：

| 策略 | 论文锚点 | `on_seal` 逻辑 |
|---|---|---|
| `TokenBlockPolicy` | PagedAttention 块化 | 一律压缩刚封口的所有块 |
| `WindowBlockPolicy` | KIVI / SKVQ 滑动窗口 | 扫描全部块，**整块跌出窗口（block_end ≤ total - window_size）的才压缩** |
| `HybridPolicy` | sink + window + 量化（StreamingLLM 风格） | WindowPolicy + 永久 fp16 sink |

策略和量化器**完全解耦**：策略只看 token 位置，不关心怎么量化。

### Layer 3 — HF Cache 适配（`hf_cache.py`）

transformers 5.x 把 Cache 拆成了**双层结构**：

```
Cache (orchestrator)
  └── self.layers: list[CacheLayerMixin]   ← 每层一个
```

我相应实现了**两个类**：

#### `BlockCacheLayer(CacheLayerMixin)`：单层 cache

持有：
- 一个 `BlockTable`
- K 的 `BlockMSECompressor`
- V 的 `BlockMSECompressor`（K/V 不对称位宽就靠这两个独立实例）

实现 v5 抽象方法：`lazy_initialization`、`update`、`get_seq_length`、`get_max_cache_shape`、`get_mask_sizes`。

核心 `update` 是整个流程的串联：

```python
def update(self, key_states, value_states):
    if not self.is_initialized:
        self.lazy_initialization(...)   # ← 第一次 update 时发现 (B, H, D)

    sealed = self.table.append(k, v)             # ← Layer 1: 块化
    to_compress = self.cfg.policy.on_seal(...)   # ← Layer 2: 决策
    for blk in to_compress:
        ck = self.k_compressor.compress(blk.fp16_k)   # ← Layer 1b → Layer 0
        cv = self.v_compressor.compress(blk.fp16_v)
        blk.to_compressed(ck, cv)

    return self._materialize(dtype)              # ← 解压回 dense (B, H, S, D)
```

#### `BlockKVCache(Cache)`：顶层 orchestrator（极薄）

```python
def update(self, k, v, layer_idx, *args, **kwargs):
    while len(self.layers) <= layer_idx:
        self.layers.append(BlockCacheLayer(self.config, layer_idx=...))
    return self.layers[layer_idx].update(k, v)
```

第一次见到 `layer_idx=N` 就 lazy 创建对应的 BlockCacheLayer。每层用不同随机种子（`seed_base + layer_idx * 1000`）生成不同的旋转矩阵 Π，避免不同层共用同一个 Π 导致量化结构相关性。

## 五、完整数据流（一次 generate 的内部）

举例：Qwen3-4B + WindowBlockPolicy(window=128) + block_size=16 + prompt 1000 tokens：

```
model.generate(input_ids, past_key_values=BlockKVCache(...))
                                                │
       ┌────────────────────────────────────────┘
       │ HF 内部 forward 走 36 层
       ▼
   ┌─ layer 0:
   │     attention 算完 K/V (1, 8, 1000, 128)  ← 8 个 KV head, head_dim=128
   │     调 cache.update(K, V, layer_idx=0)
   │       │
   │       ├── BlockKVCache.update 路由到 layers[0] (BlockCacheLayer)
   │       │
   │       ├── lazy_initialization: 建 BlockTable(block_size=16, D=128, H=8, B=1)
   │       │                        建两个 BlockMSECompressor (K=6bit, V=4bit)
   │       │                        compressor 内部建 MSECompressor(随机 Π + 码本)
   │       │
   │       ├── table.append(K, V) → 切成 62 个满块 + 1 个半满块, 返回 62 个 sealed
   │       │
   │       ├── WindowBlockPolicy.on_seal:
   │       │     窗口尾在 token 872，block_end ≤ 872 的块 = 块 0..54
   │       │     → 返回 55 个块要压缩
   │       │
   │       ├── for 每个要压缩的块:
   │       │     k_compressor.compress(blk.fp16_k)  ← Π·v̂, Lloyd-Max
   │       │       └── MSECompressor.compress: 真·TurboQuant 调用
   │       │     blk.to_compressed(...)            ← 状态机: SEALED → COMPRESSED
   │       │
   │       └── _materialize(fp16):
   │             把 55 个压缩块 decompress 回 fp16
   │             + 8 个仍是 fp16 的窗口块
   │             cat 得到 (1, 8, 1000, 128) 喂给 attention
   │
   ├─ layer 1: 同上，但用 layer_idx=1 → 不同的 Π 矩阵种子
   ├─ ...
   └─ layer 35
       │
       ▼
   logits → next token
       │
       ▼
   cache.update(K_new, V_new, layer_idx=0..35) 又来一遍 (S=1)
```

每次 `update` 调用都会重跑量化决策、压缩、解压——但已经压缩的块不会被压第二次，因为 `on_seal` 跳过非 SEALED 状态。

## 六、按汇报分类法对应分组

| 汇报里的轴 | 核心思想 | 框架对应 |
|---|---|---|
| **Token block**（按固定位置分组） | 连续 token 切固定长度，块级驱逐 / 块级量化 | ✅ `TokenBlockPolicy` |
| **Window block**（按时间窗口分组） | 最近 N 个 token 高精度，更早的低精度 | ✅ `WindowBlockPolicy` |
| **Semantic block**（按语义结构分组） | 语义簇，需要 KMeans / 分隔符 | ❌ 不实现 |

所以本框架**同时实现了前两种**，作为可切换的策略；用户选哪个用哪个，也可以混用（`HybridPolicy = sink + window + 量化块`）。代码里这条选择就是一行：

```python
cfg = BlockCacheConfig(
    policy=TokenBlockPolicy(),                    # 纯 token block
    # policy=WindowBlockPolicy(window_size=128),  # 纯 window block
    # policy=HybridPolicy(sink_size=4, window_size=128),  # 三段式
)
```

### Token Block 在框架里怎么落地

汇报里讲 token block 有两种用法：
1. **块级驱逐**：不是逐 token 删，而是整块删 / 整块保留
2. **块级量化**：多个 token 组成一个 block，块内共享一套 scale / zero-point

我做的是 **第二种（块级量化）**，第一种（驱逐）作为可扩展点留出来了——`KVBlock.importance` 字段已预留。

`TokenBlockPolicy.on_seal` 只有一行，对应"块满了就量化整块"：

```python
class TokenBlockPolicy:
    def on_seal(self, sealed, table):
        return list(sealed)   # 一律压缩
```

### Window Block 在框架里怎么落地

汇报第 50-60 行讲：
> Window block 是按 token 的时间新旧来分组——最近 N 个 token 高精度，更早的低精度，**随生成过程移动**

`WindowBlockPolicy` 直接实现这个语义：

```python
class WindowBlockPolicy:
    def on_seal(self, sealed, table):
        total = table.total_len             # 当前总长度（随生成变大）
        for blk in table.blocks:
            blk_end = cursor + blk.current_len
            in_window = blk_end > total - self.window_size
            if not in_window and blk.state == SEALED:
                to_compress.append(blk)     # 整块跌出窗口 → 量化
        return to_compress
```

**关键点**：每次 `update` 都重新扫描所有块，因为 `total` 在变。这正是汇报强调的"动态时间窗口"——一个块在 t=200 时还在窗口里（fp16），t=500 时已经被压缩了。

对照汇报里 KIVI 和 SKVQ 的差异：

| | KIVI | SKVQ | 我的 WindowBlockPolicy |
|---|---|---|---|
| recent window 是什么 | FP16 residual buffer | sliding-window 高精度 | FP16 缓冲（SEALED/FILLING 状态的块） |
| 老 token 怎么处理 | 一段量化 | group-level dynamic quant | 按块逐块量化 |
| 是否真"分组" | ❌ 汇报说 KIVI 没有按分组思想 | ✅ | ✅ |

我的实现**比 KIVI 更进一步**——不是把整段老 token 一次性量化，而是按 `block_size` 切成块逐块量化。这个"块化"借鉴了 PagedAttention 的思路，但**不需要 vLLM 的物理 page 内核**。

## 七、与 TurboQuant 的两个结合点

TurboQuant 本质是 **per-vector（逐 token）量化器**——它一次吃一堆向量 `(N, D)`，每个向量独立归一化、独立旋转、独立量化、存自己的 norm。它**不知道也不关心**这些向量在 KV cache 里是按什么方式分组的。

那么"分组 + TurboQuant"要在哪两个地方结合？

### 结合点 1：决定"何时"调用 TurboQuant ← 策略的事

```
不分组的世界：每来一个 token 就调一次 TurboQuant 量化
                  ↓
分组的世界：等够一个 block / 等出窗口 → 才调 TurboQuant 一次性量化整块
```

代码里这个决策完全在 `policy.on_seal` 里做：

```python
# hf_cache.py — BlockCacheLayer.update
sealed = self.table.append(k, v)              # 块化
to_compress = self.cfg.policy.on_seal(...)    # ← 分组策略决定何时
for blk in to_compress:
    ck = self.k_compressor.compress(blk.fp16_k)   # ← 这里才真正调 TurboQuant
    blk.to_compressed(ck, cv)
```

**所以策略对 TurboQuant 是"开关式"集成**——TurboQuant 不需要任何修改，只是被策略择时调用。

### 结合点 2：决定"块内怎么量化" ← 粒度的事

汇报第 23 行讲块级量化的特点是"**block 内共享一套或几套 scale / zero-point**"。但 TurboQuant 原生是逐向量一个 norm，**不共享任何东西**。

所以加了 `granularity` 旋钮，让 TurboQuant 可选地变成"块内共享 scale"：

```python
# quantizer.py
class BlockMSECompressor:
    def compress(self, states):
        if granularity == 'per-vector':
            return self._inner.compress(states)   # ← TurboQuant 原生：每 token 一个 norm
        else:
            # per-block: 用块均值 norm 作为 SKVQ 风格的 group-level scale
            block_norm = per_token_norm.mean(dim=1)  # ← 一块一个 scale
            scaled = states / block_norm
            rotated = scaled @ self._inner.Pi.T      # ← 复用 TurboQuant 的 Π
            indices = argmin |rotated - centroids|   # ← 复用 TurboQuant 的码本
            return {idx_bytes, block_norm, ...}
```

**关键**：per-block 模式**没有抛弃 TurboQuant**，只是改了归一化粒度，旋转矩阵 Π 和 Lloyd-Max 码本完全复用。这相当于把 TurboQuant 从"per-token 量化"升级成"group-level 量化"——直接对应 SKVQ 论文的思想。

存储对比：
```
per-vector: 每 token 存 indices + 自己的 fp16 norm
            block_size=16 → 16 × 2B = 32 B/块的 norm 开销

per-block:  每 token 只存 indices，整块共享一个 fp16 mean-norm
            block_size=16 → 1 × 2B = 2 B/块的 norm 开销
            ↑ 省了 30 B/块（不大但可观），代价是块内重建精度略降
```

### 一句话总结

> 在 TurboQuant 的 per-vector 量化器之上，加了**两个**正交的"分组"维度：
>
> - **时间维度**（policy 选择）：用 `TokenBlockPolicy` 就是汇报的 token block，用 `WindowBlockPolicy` 就是 window block——决定**什么时候**调用 TurboQuant
> - **空间维度**（granularity 选择）：per-vector 保持 TurboQuant 原汁原味，per-block 在 TurboQuant 内部做 SKVQ 风格的块内 scale 共享——决定**块内怎么**调用 TurboQuant
>
> 两个旋钮可以自由组合（4 种配置），都能跑同一个 demo 看效果。

## 八、相对单一方案的优势

### 1. 算法层：TurboQuant 的旋转**自动解决** SKVQ 的核心痛点

汇报第 8 行讲 KIVI 的核心观察：
> *Key cache 存在明显的 channel-wise outlier——某些隐藏维度数值长期偏大*

SKVQ 为此专门做 channel reorder（KMeans 聚类把相似 channel 凑一组），代价是要离线学一个 channel 排列，引入了一个超参数和一个预处理阶段。

而 TurboQuant 的 **random rotation Π 是一个数学定理级别的解法**：

$$
v \xrightarrow{\Pi} \tilde{v}, \quad \tilde{v}_i \overset{\text{iid}}{\sim} \mathcal{N}(0, 1/D)
$$

旋转后**每个坐标都服从同一分布**，channel-wise outlier 在数学意义上不存在。

**所以"TurboQuant + 块级 scale"比"SKVQ"更干净**：
- SKVQ：channel reorder（启发式）+ group-level scale + clipping
- 我的：rotation（参数无关）+ group-level scale，**不需要 channel reorder**

这是 1+1 > 2 的部分——用 TurboQuant 的旋转替换掉 SKVQ 的 channel reorder，思想上更优雅，工程上少一个超参数。

### 2. 表达力：单用 TurboQuant 做不到时间策略

原版 TurboQuant V3 只有一个 `residual_window` 参数（最近 N token fp16），**没有"块"概念**——老 token 是被一整段量化的。这意味着：

| 想做的事 | 单用 TurboQuant V3 | 框架支持 |
|---|---|---|
| sliding window（KIVI 风格） | ✅ residual_window | ✅ WindowBlockPolicy |
| 块级驱逐（PagedEviction） | ❌ 没法做 | 🔧 KVBlock 已留 importance 字段 |
| sink + window + 量化（StreamingLLM 风格） | ❌ | ✅ HybridPolicy |
| 每块独立替换量化器（早期层 8-bit, 中间层 4-bit） | ❌ 全局一个 | ✅ 每个 BlockCacheLayer 独立 |
| 块级 attention score 缓存（IceCache 风格延伸） | ❌ | ✅ 接口已对齐 |

单用 TurboQuant 是**单点优化**，加上分组就变成**一套可装配的 cache 管理系统**。

### 3. 工程层：HF 集成 = 能进真实推理路径

原 repo 的 TurboQuant 只在 `validate.py` / `generation_test.py` 这种合成测试里跑。`BlockKVCache(transformers.Cache)` 让它**第一次能直接喂给** `model.generate()`，这是从"算法 demo"到"可被使用"的一步。

## 九、局限与诚实评估

### 1. 短上下文（<1K token）—— 收益微乎其微

block_size=16 + window=128 在 1K 上下文下，量化的块只有 (1024-128)/16 ≈ 56 块。这个量级下，**TurboQuant V3 的 residual_window 已经够用**——它简单粗暴一刀切，没有块的开销，效果一样。

```
1K context, K6V4:
  TurboQuant V3 (residual_window=128):  压缩比 ~1.8x
  我的 WindowBlock (window=128):        压缩比 ~1.8x
  收益差异 < 5%
```

### 2. 没改 attention kernel = 运行期峰值显存几乎没省

这是 MVP 最大的妥协。框架每次 attention 之前会把压缩块解压回 fp16 拼接。意味着：

| 场景 | 持久存储 | attention 那一刻的峰值 |
|---|---|---|
| FP16 baseline | 100% | 100% |
| **本框架** | **30-50%** ✅ | **~95%** ❌ |
| KIVI / SKVQ（自定义 kernel） | 30-50% ✅ | **30-50%** ✅ |

所以如果目标是"在 8GB 卡上跑更长上下文"，**单用 KIVI/SKVQ 的内核版本会更直接**。本框架更适合：
- CPU offload 场景（持久存储省了就有意义）
- 算法/分组策略的研究对比（拼装方便）
- 教学和 ablation（每个旋钮独立可调）

### 3. 块化对极低位（2-bit / 1.5-bit）**不一定**比 SKVQ 强

SKVQ 在论文里能稳定做到 2-bit K + 1.5-bit V。本框架在 K4V2 测过 5x 压缩，但 generation 质量已经塌了——同等 bit 预算下，**SKVQ 因为有 channel reorder 的 fine-tuning，质量上限可能高于本方案**。

本方案优势是**简单**和**可拆解**，不是**极限压缩比**。

### 4. Per-block granularity 是一把双刃剑

per-block scale 和 TurboQuant 的 Lloyd-Max 码本**理论上不完全匹配**——码本是按单位方差高斯校准的，per-block 模式下块内向量方差不严格归一。8-bit 时几乎看不出差距（实测 0.78% vs 0.77%），4-bit 时 per-block 就明显不如 per-vector。

所以这个旋钮**不是无脑开**。

## 十一、综合判断与适用场景

本框架**不是**算法上的新发明，而是**一个组合性的研究/工程平台**。

### 它的真实价值场景

1. **教学和 ablation**：想做"分组方式 × 量化粒度"的 2×2×2 对照实验，单用 TurboQuant 或 SKVQ 都做不到，得自己写——本框架就是替你写好的脚手架。

2. **CPU offload 长上下文**：持久存储省 2-3x 即有意义，attention 峰值没省也无所谓。

3. **快速试错新策略**：写一个新的 `GroupingPolicy` 子类只要 10-20 行（比如 attention-based importance、layer-adaptive bits 等），不用碰量化代码。

4. **作为论文 baseline**：如果最终想发论文，提出一个新分组方法时，需要和 TurboQuant、SKVQ、PagedEviction 横向对比——本框架可以**用同一份代码**跑这些 baseline，公平性强。

### 它的真实价值不在哪里

1. 不是单任务下的最强方案——同等 bit 预算 + 自定义 kernel 下，SKVQ 论文方案大概率更好。
2. 不能替代生产环境的 vLLM/TRT-LLM——没有 CUDA kernel 优化。
3. 极限压缩比（2-bit 以下）不是它的目标。

### 对汇报场景的具体建议

如果导师问"为什么不直接用 SKVQ 或 TurboQuant"，建议这么答：

> 单用某个方法只能验证一个点。这个框架的目的是**把"分组思想"和"量化算法"解耦**——分组策略可换、量化粒度可换。这样：
>
> 1. 可以**复现** TurboQuant V3（policy=Token, granularity=per-vector）
> 2. 也可以**复现** SKVQ 思想（policy=Window, granularity=per-block）
> 3. 还可以**做 SKVQ 没做的事**：用 TurboQuant 的旋转替换它的 channel reorder，看是否同样有效（一个干净的对照实验）
> 4. 留出接口给后续 PagedEviction 风格的块级驱逐
>
> **这是研究脚手架不是产品**，目标是让后续每个新想法都能用最少的代码塞进来对比。

这个定位讲清楚就不会被批"为什么不直接用现成方案"。
