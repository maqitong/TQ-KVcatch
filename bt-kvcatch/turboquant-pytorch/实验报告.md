## 二、代码介绍

### 2.1 项目概述

本项目是 TurboQuant（ICLR 2026）的 PyTorch 实现，核心贡献是在原有 TurboQuant 量化算法之上增加了**块结构化 KV cache 管理**和**可插拔分组策略**，将"分组思想"与"量化算法"解耦，形成一套可扩展的研究框架。

### 2.2 四层架构

```
Layer 4  实验 / Demo                  experiment.py · demo.py · benchmark.py
─────────────────────────────────────────────────────────────────────────────
Layer 3  HuggingFace Cache 适配       BlockKVCache(Cache)
               └── [BlockCacheLayer]_n    per-layer
─────────────────────────────────────────────────────────────────────────────
Layer 2  分组策略（Strategy 接口）    TokenBlockPolicy · WindowBlockPolicy · HybridPolicy
─────────────────────────────────────────────────────────────────────────────
Layer 1  块抽象 + 量化包装            KVBlock · BlockTable · BlockMSECompressor
─────────────────────────────────────────────────────────────────────────────
Layer 0  TurboQuant 原语（已有）      MSECompressor (random rotation + Lloyd-Max)
```

每层之间**单向依赖**，要换分组策略只动 Layer 2，要换量化算法只动 Layer 1，上层不用改。

### 2.3 核心模块说明

#### Layer 0 — TurboQuant 原语 (`compressors_v3.py`)

TurboQuant 的核心算法是**两步走**：

1. **随机旋转**：将向量乘以随机正交矩阵 $\Pi$，使旋转后每个坐标近似独立同分布的高斯 $\mathcal{N}(0, 1/D)$
2. **Lloyd-Max 量化**：对旋转后的每个坐标做标量量化，码本按单位方差高斯最优校准

```
输入向量 v ∈ ℝᴰ
     │
     ① 归一化     v̂ = v / ‖v‖              ← 存 ‖v‖ (fp16)
     │
     ② 随机旋转   r = Π · v̂                ← Π 是固定的随机正交矩阵
     │
     ③ 逐坐标量化  iⱼ = argmin |rⱼ − cₖ|   ← Lloyd-Max 码本
     │
     输出: bit-packed indices + ‖v‖
```

`MSECompressor` 封装了这一流程，提供 `compress(states) -> dict` 和 `decompress(dict) -> tensor` 接口。

`TurboQuantV3` 在 `MSECompressor` 之上增加了：
- **不对称 K/V 位宽**：Key 用更多 bit（Key 对量化更敏感）
- **残差窗口**：最近 N 个 token 保持 FP16 不压缩
- **层自适应精度**：首尾层用更高位宽（protected_layers）

#### Layer 1 — 块抽象 (`blocks.py`) + 量化包装 (`quantizer.py`)

**KVBlock** 是固定容量的 KV 槽位，包含三态状态机：

```
FILLING  ──── 块满 ────►  SEALED  ──── 策略决定 ────►  COMPRESSED
(fp16)                     (fp16)                        (TurboQuant)
```

**BlockTable** 是单层的有序块列表，负责将输入的 `(B, H, n, D)` 张量自动切片路由到各个 KVBlock。

**BlockMSECompressor** 是 TurboQuant 与块框架的桥梁，提供两种量化粒度：
- `per-vector`：每个 token 向量独立归一化，存各自的 fp16 norm（TurboQuant 原生方式）
- `per-block`：整个块共享一个 mean-L2-norm 标量（SKVQ 风格的 group-level 量化），复用 TurboQuant 的旋转矩阵和码本

#### Layer 2 — 分组策略 (`policies.py`)

策略只回答一个问题：**哪些 SEALED 块应该被立刻压缩？**

| 策略 | 论文锚点 | 决策逻辑 |
|------|----------|----------|
| `TokenBlockPolicy` | PagedAttention 块化 | 所有 SEALED 块一律压缩 |
| `WindowBlockPolicy` | KIVI 滑动窗口 | 只有**整块跌出窗口**的才压缩 |
| `HybridPolicy` | StreamingLLM 风格 | sink 永久 FP16 + window + 窗口外压缩 |

**关键设计**：策略和量化器完全解耦。策略只看 token 位置信息，不关心如何量化。

#### Layer 3 — HF Cache 适配 (`hf_cache.py`)

`BlockKVCache` 继承自 `transformers.Cache`，可直接作为 `model.generate(past_key_values=cache)` 参数使用。

核心流程：

```
model.generate(input_ids, past_key_values=BlockKVCache(...))
       │
       │  HF 内部 forward 走 36 层
       ▼
  每层 attention 算完 K/V 后调 cache.update(K, V, layer_idx)
       │
       ├── BlockTable.append() → 切块，FILLING → SEALED
       ├── policy.on_seal() → 决定哪些块要压缩
       ├── 对要压缩的块调 BlockMSECompressor.compress()
       │       └── 内部调 MSECompressor.compress() ← TurboQuant 原语
       └── _materialize() → 解压 + 拼接回 (B, H, S, D) 给 attention
```

### 2.4 核心数据流

```
新 K, V (B, H, n, D)
        │
        ▼
BlockKVCache.update(layer_idx)
        │
        ├── 路由进当前层的 BlockTable.append()
        │       └── 切成多个 KVBlock，FILLING → SEALED
        │
        ├── policy.on_seal(sealed_blocks)
        │       ├── TokenBlockPolicy: 一律量化
        │       ├── WindowBlockPolicy: 整块跌出窗口才量化
        │       └── HybridPolicy: sink fp16 + window + 量化
        │
        ├── 对要量化的块调 BlockMSECompressor.compress
        │       └── 复用 TurboQuant 的旋转 + Lloyd-Max
        │
        └── 解压所有块 + 拼接回 (B, H, S_total, D) 给 attention
```

### 2.5 与论文方法的对应关系

| 论文方法 | 本框架对应 |
|----------|-----------|
| TurboQuant (ICLR 2026) | `MSECompressor`：random rotation + Lloyd-Max |
| PagedAttention 块化 | `BlockTable` + `KVBlock`：固定 block_size 分块 |
| KIVI residual window | `WindowBlockPolicy`：窗口外整块量化 |
| SKVQ group-level quantization | `per-block` 粒度：块内共享 scale |
| StreamingLLM attention sink | `HybridPolicy`：sink 永久 fp16 |

## 三、实验设计

### 3.1 实验方法

采用 **Needle-in-a-Haystack（大海捞针）** 测试法：
- 在一段由重复填充文本构成的"干草堆"中插入一个特定的"针"信息
- 让模型回答关于"针"的问题，检验模型能否在长上下文中准确定位信息
- 如果模型回答正确则记为 **FOUND**，否则记为 **MISS**

具体配置：
- 针：`"The secret project code name is AURORA-7749."`
- 期望回答：`"AURORA-7749"`
- 针的插入位置：干草堆中间（约 50% 处）
- 提问方式：`"What is the secret project code name? Answer with just the code name."`

### 3.2 对比方法

共 5 种方法参与对比：

| 编号 | 方法 | 说明 |
|------|------|------|
| A | **FP16 baseline** | 无压缩，全部 FP16 存储，质量上限参考 |
| B | **TurboQuant V3 (flat)** | 原版 V3Cache，整段压缩 + residual_window=128 |
| C | **TokenBlock + TQ** | 块满即压缩，PagedAttention 风格 |
| D | **WindowBlock + TQ** | 窗口外才压缩，KIVI 风格 |
| E | **Hybrid + TQ** | sink(4) + window(128) + 压缩，StreamingLLM 风格 |

### 3.3 三组实验

#### 实验 1：压缩比 vs 检索质量（主实验）

- **目的**：在固定量化参数下，对比 5 种方法在不同上下文长度下的检索质量和压缩比
- **固定参数**：K=6bit, V=4bit, block_size=16, window=128
- **变量**：上下文长度 = 1024, 2048, 3072, 4096
- **指标**：检索质量 (FOUND/MISS) + 压缩比

#### 实验 2：位宽扫描（压缩极限探索）

- **目的**：找到各方法的质量崩溃点（quality cliff）
- **固定参数**：上下文=2048, block_size=16, window=128
- **变量**：位宽配置 = K8/V4, K6/V4, K4/V4, K4/V3, K4/V2
- **参与方法**：TQ V3 flat, TokenBlock, WindowBlock（3 种压缩方法）
- **指标**：检索质量 + 压缩比

#### 实验 3：量化粒度对比（per-vector vs per-block）

- **目的**：对比 TurboQuant 原生逐向量量化与 SKVQ 风格逐块量化的效果差异
- **固定参数**：WindowBlock policy, ctx=2048, window=128, block_size=16
- **变量**：粒度 = per-vector, per-block；位宽 = K6/V4, K4/V4, K4/V3
- **指标**：检索质量 + 压缩比 + 耗时

### 3.4 实验运行

实验脚本为 `turboquant/block_cache/experiment.py`，运行命令：

```bash
conda activate kvcatch
cd D:\KVcatch\bt-kvcatch\turboquant-pytorch
python -m turboquant.block_cache.experiment
```

可通过 `--skip-exp 1 2 3` 跳过指定实验。

## 四、实验结果

### 4.1 实验 1：压缩比 vs 检索质量

**配置**：K6/V4, block_size=16, window=128

#### 检索质量（FOUND = 检索成功）

| 方法 | 1024 | 2048 | 3072 | 4096 |
|------|------|------|------|------|
| FP16 baseline | FOUND | FOUND | FOUND | FOUND |
| TQ V3 flat rw=128 | FOUND | FOUND | FOUND | FOUND |
| TokenBlock + TQ | FOUND | FOUND | FOUND | FOUND |
| WindowBlock + TQ | FOUND | FOUND | FOUND | FOUND |
| Hybrid + TQ | FOUND | FOUND | FOUND | FOUND |

**结论**：在 K6/V4 位宽下，所有压缩方法在 1024~4096 上下文范围内均能正确检索目标信息，质量与 FP16 基线一致。所有方法均精确输出 `"AURORA-7749"`，与 FP16 基线完全一致。

#### 压缩比

| 方法 | 1024 | 2048 | 3072 | 4096 |
|------|------|------|------|------|
| FP16 baseline | 1.00x | 1.00x | 1.00x | 1.00x |
| TQ V3 flat rw=128 | 2.48x | 2.76x | 2.87x | 2.93x |
| TokenBlock + TQ | 2.58x | 2.60x | 2.61x | 2.60x |
| WindowBlock + TQ | 2.16x | 2.37x | 2.45x | 2.48x |
| Hybrid + TQ | 2.16x | 2.37x | 2.45x | 2.48x |

**观察**：
- 所有压缩方法均实现了 **2.1x~2.9x** 的压缩比
- V3 flat 的压缩比最高，因为它不按块切分、管理开销更小
- 随着上下文增长，所有方法的压缩比均稳步提升（量化块占比增大）

### 4.2 实验 2：位宽扫描

**配置**：ctx=2048, block_size=16, window=128

#### 检索质量

| 方法 | K8/V4 | K6/V4 | K4/V4 | K4/V3 | K4/V2 |
|------|-------|-------|-------|-------|-------|
| TQ V3 flat | FOUND | FOUND | MISS | MISS | MISS |
| TokenBlock | FOUND | FOUND | MISS | MISS | MISS |
| WindowBlock | FOUND | FOUND | MISS | MISS | MISS |

**结论**：
- **K6/V4 是质量安全的下界**，K8/V4 和 K6/V4 均能正确检索，输出 `"AURORA-7749"`
- **K4/V4 是质量崩溃点**，所有方法在此位宽下均检索失败
- K4/V4 时模型输出变为 `"AURORA"`（缺少 `-7749` 后缀）或 `"AURORA7749"`（缺少连字符），说明 4-bit Key 量化导致精确匹配能力下降
- K4/V3 和 K4/V2 进一步恶化，输出 `"AURORA-7449"`（数字错误）或 `"AURORA774"`（截断），量化误差已影响数字识别
- Key 量化到 4-bit 时信息损失过大，即使 Value 保持 4-bit 也无法恢复

#### 压缩比

| 方法 | K8/V4 | K6/V4 | K4/V4 | K4/V3 | K4/V2 |
|------|-------|-------|-------|-------|-------|
| TQ V3 flat | 2.38x | 2.76x | 3.30x | 3.65x | 4.09x |
| TokenBlock | 2.60x | 2.60x | 3.80x | 3.80x | 4.97x |
| WindowBlock | 2.37x | 2.37x | 3.29x | 3.28x | 4.08x |

**观察**：
- 压缩比随位宽降低近似线性增长
- K4/V2 可达 ~5x 压缩，但质量完全不可用
- 在质量可接受的范围（K6/V4 以上），实际压缩比约 2.0x~2.7x

### 4.3 实验 3：量化粒度对比

**配置**：WindowBlock, ctx=2048, window=128, block_size=16

#### K6/V4 粒度对比

| 粒度 | 检索质量 | 压缩比 | 耗时 |
|------|----------|--------|------|
| per-vector | FOUND | 2.37x | 77.6s |
| per-block | FOUND | 2.41x | 77.7s |

**结论**：在 K6/V4（质量安全区）位宽下，per-vector 和 per-block 表现几乎一致，两种粒度均能正确检索。

#### 扩展扫描：不同位宽下的粒度对比

| 位宽 | per-vector | per-block |
|------|-----------|-----------|
| K6/V4 | FOUND (2.37x) | FOUND (2.41x) |
| K4/V4 | MISS (3.29x) | MISS (3.32x) |
| K4/V3 | MISS (3.28x) | MISS (3.32x) |

**结论**：在低位宽下，两种粒度均无法保持质量，粒度选择对结果影响不大。

## 五、实验分析

### 5.1 压缩质量分析

#### 质量安全区与崩溃点

实验数据表明存在清晰的质量分层：

```
                    质量安全区
K8/V4 ──────────── K6/V4 ───┬── K4/V4 ─── K4/V3 ─── K4/V2
     FOUND  FOUND  FOUND    │    MISS     MISS     MISS
                           崩溃点
```

**Key 的量化位宽是质量的决定因素**。当 Key 从 6-bit 降到 4-bit 时，检索准确率从 100% 骤降到 0%。这是因为：
1. Key 在 attention 计算中承担 query-key 匹配职责，精度直接影响检索准确性
2. 4-bit Lloyd-Max 量化仅有 16 个码字，对 Key 向量的区分度不足
3. Value 相对更宽容——V4 和 V3 的差异不如 K6 和 K4 那么剧烈

#### 不对称 K/V 位宽的合理性

实验结果验证了 TurboQuant V3 的核心设计选择——**Key 用更多 bit，Value 可以更少**：
- K6/V4（安全）vs K4/V4（崩溃）：Key 多 2-bit 决定了成败
- K4/V4（崩溃）vs K4/V2（也崩溃但压缩比更高）：在 Key 已经崩溃后，Value 的位宽无关紧要

### 5.2 分组策略对比分析

#### 各策略特点

| 策略 | 压缩比 | 特点 |
|------|--------|------|
| TokenBlock | 2.60x@2048 | 最激进，块满即压。压缩块占比最高 |
| WindowBlock | 2.37x@2048 | 保守，保留窗口内 FP16。近期 token 质量最高 |
| Hybrid | 2.37x@2048 | 折中，sink 永久保护 + 窗口保护 |
| V3 flat | 2.76x@2048 | 不按块切分，管理开销最小 |

在 K6/V4（质量安全区）位宽下，三种策略的检索质量完全一致（全部 FOUND），差异仅在压缩比上。

#### 策略选择的建议

- **追求最大压缩**：TokenBlock（块满即压，压缩比略高）
- **追求近期 token 质量**：WindowBlock（窗口内 FP16 保护）
- **需要 attention sink 保护**：Hybrid（首 N 个 token 永久 FP16）

### 5.3 量化粒度分析

per-vector 和 per-block 在 K6/V4 下表现一致，说明：

1. **在高价位宽下，粒度差异可以忽略**——6-bit 有 64 个码字，足以覆盖块内方差
2. **per-block 的存储节省有限**——每块仅省 30 字节（16 个 fp16 norm → 1 个），相对整体存储微不足道
3. **TurboQuant 的随机旋转足够强**——旋转后坐标近似同分布，不需要 SKVQ 的 channel reorder 预处理

### 5.4 上下文长度的影响

压缩比随上下文增长而提升：

| 上下文 | WindowBlock 压缩比 | 量化块占比 |
|--------|-------------------|-----------|
| 1024 | 2.16x | ~87% |
| 2048 | 2.37x | ~94% |
| 3072 | 2.45x | ~96% |
| 4096 | 2.48x | ~97% |

原因：窗口大小固定为 128，上下文越长，被量化的 token 占比越高，压缩比越接近理论极限。

### 5.5 框架优势总结

与单独使用 TurboQuant V3 相比，块结构化框架的优势体现在：

1. **可扩展的分组策略**：V3 只有一个 residual_window 参数，本框架支持 TokenBlock/WindowBlock/Hybrid 三种策略自由切换
2. **块级管理**：V3 整段量化老 token，本框架按 block_size 逐块量化，支持未来的块级驱逐
3. **HF 集成**：`BlockKVCache` 可直接用于 `model.generate()`，V3 需要手写缓存管理
4. **量化粒度可选**：per-vector 保持 TurboQuant 原生，per-block 实现 SKVQ 风格的 group-level 量化
5. **策略与量化解耦**：新增分组策略只需 ~20 行代码，无需触碰量化逻辑

## 六、总结

### 6.1 工作成果

1. **完成了本地环境搭建**：在 T1000 8GB 显卡上搭建了完整的 conda 开发环境，使用 4-bit 量化加载 Qwen2.5-3B-Instruct 模型，解决了显存限制问题。

2. **开发了块结构化 KV cache 框架**：在 TurboQuant 量化算法之上，实现了块管理（KVBlock 状态机）、可插拔分组策略（TokenBlock/WindowBlock/Hybrid）和 HuggingFace 集成（BlockKVCache），新增约 800 行代码，不改动原有实现。

3. **设计了三组对比实验**：分别从"压缩比 vs 质量"、"位宽极限"和"量化粒度"三个维度进行系统评测，共覆盖 5 种方法 × 多种配置组合。

4. **实验结果表明**：
   - 在 K6/V4 位宽下，所有方法在 1024~4096 上下文范围内均实现 2.16x~2.93x 压缩比，且检索质量与 FP16 基线一致
   - Key 量化位宽是质量的决定因素，K4 是质量崩溃的临界点
   - 三种分组策略在质量安全区内表现一致，差异主要体现在压缩比上
   - per-vector 和 per-block 粒度在高位宽下效果相同

### 6.2 框架定位

本框架是一个**组合性的研究平台**，而非单一的最优方案。其价值在于：

- **解耦设计**：分组策略与量化算法独立可换，支持公平的横向对比实验
- **可扩展**：新增分组策略只需继承 `GroupingPolicy` 并实现 `on_seal` 方法
- **教学友好**：每个组件职责单一，代码量小，适合理解和修改
- **论文 baseline**：可在同一份代码上复现 TurboQuant V3、KIVI 思想、SKVQ 思想的变体

### 6.3 已知局限

1. **运行期解压**：当前 MVP 在 attention 前解压回 FP16，瞬时显存收益有限。真正的显存节省发生在持久化存储层面（CPU offload / 长上下文场景）
2. **质量安全的压缩比上限**：在 K6/V4 下约 2.3x~2.7x，低于文献中 SKVQ 的极限压缩比（SKVQ 可稳定做到 2-bit/1.5-bit，但需要 channel reorder 的 fine-tuning）
3. **短上下文收益有限**：1024 token 以下，框架的块化管理开销与压缩收益基本持平

### 6.4 未来方向

1. **自定义 attention kernel**：实现不解压的 compressed attention，彻底降低运行期峰值显存
2. **块级驱逐**：利用已预留的 `KVBlock.importance` 字段，实现基于 attention score 的 PagedEviction 风格驱逐
3. **层自适应策略**：不同层使用不同的量化位宽（如首尾层 8-bit、中间层 4-bit），进一步提升压缩比
4. **更大模型与更长上下文**：在更大参数模型和 8K+ 上下文下验证框架的扩展性
